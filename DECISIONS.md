## D-002 — Organization Modeling

`Club`, `Society`, and `Startup` share ~80% of their fields (name, logo, description, members, events, announcements). They are modeled as a single `organizations` table with a `type` enum (`club | society | startup`) plus an optional `startup_details` extension table for startup-only fields (industry, stage, website, funding_stage). This avoids duplicate table/component logic while preserving distinct routes (`/clubs`, `/startups`) at the API/frontend layer via filtered queries.

## D-003 — Role Verification

Self-declared roles (`professor`, `researcher`, `club_rep`, `startup_member`, `alumni`) are stored as *requested* on `users.requested_role` at signup but do not grant privileges. A `verifications` table tracks admin-reviewed approval per user per role claim. Only `role = student` and `role = pending` are auto-granted. All privileged UI/API gating checks `verifications.status = 'approved'`, never `users.requested_role` alone.

## D-004 — Privacy Enforcement Location

Field-level privacy (Section 5 of spec) is enforced in the **service layer**, not the database and not the frontend. Every profile-read service function accepts a `viewerContext` (viewer id, role, connection status) and strips fields server-side before the response leaves the API. This is documented explicitly because it is the most safety-critical rule in the whole spec (private data must never leak via API/frontend).

## D-011 — Phase 4: Verification/Reset Tokens Without a Schema Change; Role-Set Clarification; Resend via HTTP

**Context:** implementing Phase 4 (Authentication + Authorization) surfaced three gaps between the documentation and what could be literally implemented.

**1. No table for email-verification or password-reset tokens.**
`API_CONTRACT.md` §1 requires `POST /auth/verify-email {token}` and `POST /auth/reset-password {token, newPassword}`, but `DATABASE_SCHEMA.md`/the Prisma schema only has `refresh_tokens` — no table exists to persist or revoke a verification/reset token. Rather than add a schema table (the Phase-2-owned path this repo's protocol requires stopping and asking about first), a **stateless, self-verifying JWT** was used for both purposes instead:
- Both are signed with `JWT_ACCESS_SECRET` (the only general-purpose secret `ENVIRONMENT.md` documents besides the session-refresh secret) and carry a `purpose` claim (`email_verification` | `password_reset`) so one can never be replayed as the other or as a normal access token.
- Email-verification tokens are naturally idempotent (re-using one just re-confirms an already-verified account), so no revocation store is needed for them.
- Password-reset tokens embed a short fingerprint (`sha256(passwordHash).slice(0,16)`) of the password hash *at issue time*. On reset, the fingerprint is recomputed from the user's *current* password hash and compared — so the token is automatically invalidated the instant the password changes (by that reset or any other means), giving single-use behavior without a revocable DB row.
This avoids a schema change entirely. If a future phase needs auditability of verification/reset attempts (e.g., for the admin panel), that's a new, additive table — not a retrofit of this mechanism — and should get its own `DECISIONS.md` entry.

**2. Refresh tokens are JWTs, not opaque random strings.**
`ENVIRONMENT.md` documents `JWT_REFRESH_SECRET` as required, described as "sign/verify refresh tokens" — i.e., refresh tokens are expected to be JWTs, not opaque tokens. Implemented as: a JWT (`{ sub, jti, purpose: "refresh" }`) signed with `JWT_REFRESH_SECRET`, expiry `JWT_REFRESH_TTL`. The JWT itself is additionally hashed (`sha256`) and stored in `refresh_tokens.token_hash` exactly as `ARCHITECTURE.md` §3 already specified ("stored hashed... for revocation support") — so a refresh attempt must pass both JWT signature/expiry verification *and* a live, non-revoked DB row. This uses both documented JWT secrets for their evidently intended purposes and preserves revocation.

**3. Role-set for D-003 privileged-role verification: schema, not prose, is authoritative.**
D-003's prose lists `alumni` among roles requiring admin-reviewed `verifications` approval. But `DATABASE_SCHEMA.md`'s own `verifications` table definition says `role_claimed (enum, same set as requested_role minus student/alumni)`, and the Prisma `VerificationRoleClaim` enum (Phase 2) implements exactly that — excluding both `student` and `alumni`. Per this repo's priority order (actual schema > prose describing it), `requireRole` treats `student` and `alumni` as auto-granted and requires an `approved` `verifications` row for `professor`, `researcher`, `club_rep`, `startup_member`, and `admin`. D-003 itself is not edited (per this file's "later agents MUST NOT silently override an entry" rule) — this entry is the correction on record.

**4. Resend integration via direct HTTP call, not the `resend` npm SDK.**
The implementing session's sandbox had no package-registry access, so the `resend` SDK (listed in `DEPENDENCIES.md` as "resend (or chosen provider)") could not be installed. `ResendEmailService` calls Resend's plain REST endpoint (`POST https://api.resend.com/emails`) via the platform's native `fetch` instead. The `EmailService` interface is unchanged, so swapping in the official SDK later (once installable) requires no change to `auth.service.ts` or anything that consumes `emailService`. No dependency was added to `DEPENDENCIES.md` for this — none was installed.

Every one of these repository methods is called by a service function that returns the Prisma result **directly** to its controller, which calls `res.json(result)` with no intermediate field-level mapping (confirmed by reading `project.service.ts`, `event.service.ts`, `researchTeam.service.ts`, `organization.service.ts`, `conversation.service.ts`, `publication.service.ts`, `admin.service.ts`, `connection.service.ts` — every `getById`/`list`/`create`/`updateStatus` is a thin pass-through). Since a bare Prisma `include: { user: true }` (or `creator: true` / `pi: true` / etc.) returns **every scalar column** on the related row, this means **`users.password_hash` was present in the JSON response body** on: `GET /projects/:id`, `GET /events/:id`, `GET /research-teams/:id`, `GET /organizations/:slug`, `GET /conversations/:id` and its messages, `GET /publications/:id` and `GET /research-topics/:slug`, `POST/PATCH /connections*`, `GET /connections`, and `GET/PATCH /admin/verifications*` and `/admin/reports*`. This is a direct, severe violation of D-004 ("private data must never leak via API/frontend") — arguably the single most sensitive column in the schema, leaking on more than half the Phase 5 endpoint surface.
4. Confirmed via `grep` that **no downstream code anywhere reads a field off these nested objects beyond passthrough** (no `.creator.email`, `.pi.fullName`, etc. — this project has no Phase 6+ frontend consuming these fields yet), meaning the fix has zero functional-behavior risk: only unused, unintentionally-fetched columns are being removed from the wire format.

**Decision:** two-part fix, both completed this session (schema/code only — see the "not verified" note below):

- **Unconditional floor (all nested-user relations, everywhere):** added `apps/api/src/utils/prismaSelects.ts` exporting `SAFE_USER_SELECT` (`id`, `username`, `avatarUrl`, `requestedRole`) and `SAFE_USER_SELECT_ADMIN` (adds `email`, `status` — admin-only endpoints, where the caller is already `requireRole(['admin'])` and genuinely needs to identify the account under review). Replaced every bare `xxx: true` User-relation include across the 10 files listed above with `xxx: { select: SAFE_USER_SELECT }` (or `_ADMIN` for the two admin.repository.ts call sites). This is intentionally a *lower, unconditional* layer than `privacy.service.ts`'s viewer-aware filtering — it guards a leak surface that filtering was never wired into, and applies regardless of who's asking.
- **Viewer-aware layer (research-topics reverse listing specifically):** `researchTopic.repository.ts`'s `findBySlug` now selects `privacySettings` alongside each interested user's role-profile, and `researchTopic.service.ts#getBySlug` now (a) computes viewer context once per request (one `findByIdLean` + one accepted-connections query, reused via a `Set` for every listed user's `isConnected` check — not a per-user N-query pattern), (b) gates list inclusion on each user's own `researchVisibility` via `privacyService.isAllowed` (now `public`, was `private` — a pure stateless helper, safe to expose), and (c) runs each included user's embedded profile through the existing `privacyService.filterProfileForViewer` before returning it — the exact same function `GET /users/:username` already uses, so `cgpa`/social-links/academic-info now respect each user's own settings here too, not just on their own profile page. This required making `GET /research-topics/:slug` viewer-aware without requiring auth: extracted the inline `optionalAuth` middleware that `users.routes.ts` already had (identical logic, now shared) into `apps/api/src/middleware/optionalAuth.ts`, and applied it to `researchTopics.routes.ts`'s `GET /:slug` alongside passing `req.user?.id` through the controller.
- Added a dedicated regression test in `apps/api/tests/privacy-service.test.ts` is out of scope for the researchVisibility gate specifically (that logic now lives partly in `researchTopic.service.ts`, which has no existing DB-independent unit-test file — see "not verified" below).

**Why `SAFE_USER_SELECT` doesn't include `email`/`phone`:** every one of the fixed call sites is a *third-party* view of a user (a project's creator, a team's PI, a message's sender, a connection's counterpart) — none of these are "look at your own profile" or "look at a profile page" contexts where `privacy.service.ts`'s full field-level gating already applies. Until a genuine product need for showing (say) a project creator's email inline in a project card is specified, the conservative default is to expose only what's needed to identify/display someone (`id`, `username`, `avatarUrl`, `requestedRole`) and nothing privacy-sensitive. If a future phase needs more, that's a new, deliberate decision — not a default to fall back into.
